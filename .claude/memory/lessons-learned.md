Append-only. After every engagement (Phase 7 retrospective) the
orchestrator adds an entry here; at the start of every new engagement
the memory-retrieve hook surfaces relevant entries by keyword match on
the current prompt (RETRIEVE), and each entry carries a Status field
the orchestrator updates when a lesson is actually put to the test
(JUDGE). Pattern from metaswarm's post-merge reflection
(github.com/dsifry/metaswarm), rohitg00/pro-workflow's compounding
memory, and the RETRIEVE-JUDGE-DISTILL-CONSOLIDATE learning pipeline
concept from ruvnet/ruflo (adapted here as plain-text/grep, not a
vector database — unnecessary at this company's memory size).

### 2026-06-22 — doh-flight-checker — .gitignore missed .env exclusion
- **What happened:** The project scaffold didn't exclude `.env`; caught later during the Market Compass security pass rather than at creation time.
- **Lesson:** Scaffolding steps silently skip security defaults unless checked explicitly.
- **Rule going forward:** Every new project's first commit must include a `.gitignore` that covers `.env`/`.env.local`/credentials — verified, not assumed (now in secure-coding.md checklist).

### 2026-07-02 — market-compass — GitHub Pages first deploy required manual settings
- **What happened:** Deploy failed 3× at `deployment_queued`: Pages source and Actions write-permissions had to be set manually in repo Settings before any workflow-based deploy could succeed; `enablement: true` was rejected ("Resource not accessible by integration").
- **Lesson:** First-ever Pages deployment on a repo is an account-settings problem, not a workflow problem — retrying the pipeline cannot fix it.
- **Rule going forward:** Before the first Pages deploy on any repo, confirm with the user: Settings → Pages → Source = GitHub Actions, and Settings → Actions → Workflow permissions = Read and write. Escalate to the user after 2 failed identical attempts (codex-rescuer rule 5).

### 2026-07-10 — market-compass — parallel sessions on one branch cause push rejections
- **What happened:** Multiple sessions pushed to `claude/jolly-newton-5uctey` simultaneously; pushes were rejected and required fetch+merge before every push, and one rerun failed on a stale duplicate artifact.
- **Lesson:** Shared-branch parallel work needs fetch-merge-push discipline every time, and reruns of partially-failed workflows can collide with stale artifacts — a fresh run is safer.
- **Rule going forward:** Always `git fetch` + merge before push; prefer a new triggering commit over rerunning a failed workflow when artifacts may be stale.

### 2026-07-15 — market-compass — Predic panel: the data-source gate is the whole engagement, not a detail
- **What happened:** A "build a 17-section equity-research report panel" feature-add turned entirely on one reconnaissance finding — the app is PSX-Data-Portal-only and no free source publishes PSX financial statements, so ~11 of 17 sections have NO real data and could only be filled by fabricating figures (Constitution-forbidden). Shipped a fork-agnostic engine whose `SourcedFigure` discriminated union + `guard()` makes fabrication structurally impossible; unavailable sections render honest N/A. 38 Predic tests green, tsc 0, build 0. Auditor caught that a numeric BUY/SELL verdict crosses into regulated-investment-advice territory and that `VITE_`-prefixed keys leak into the client bundle.
- **Lesson:** For any "generate an analyst/report/insight" feature, verify the real data supply BEFORE any UI/spec work — the honest answer may be "this cannot be built as asked," and surfacing that fork is the deliverable. Enforce no-invented-data in the TYPE SYSTEM (a value that structurally cannot exist without {source, asOf}), not in review. A rendered verdict/score on real securities is a governance surface (disclaimer adjacent to the verdict, keys server-side only), independent of the data gap. Also: full-suite runs surface pre-existing red tests — always separate "did we regress" (check `git diff --name-only` on the failing file) from "was it already broken."
- **Rule going forward:** Feature requests that produce numbers/verdicts must (1) pass a data-source gate first with an explicit sourceable-vs-blocked matrix, (2) route every figure through a guard constructor so fabrication is a compile error, never a placeholder, and (3) get an auditor pass whenever output could read as advice or a record. `VITE_`-prefixed env vars are client-public by construction — never a secret. Pre-existing test failures on an untouched file are not a regression; prove it with the diff before claiming or denying a green suite.

### 2026-07-10 — catch-the-falling-stars — conditional module.exports makes browser games unit-testable
- **What happened:** Full 6-phase engagement on a zero-dependency canvas game. Structuring game.js as pure-logic → engine → DOM adapter, with `if (typeof module !== 'undefined') module.exports = {...}`, let Node run 21 real assertions (collision, difficulty, scoring, storage sanitization, end-of-round precedence) against the exact shipped file — no browser needed for the QA gate. ### 2026-07-30 — gold-signal-analyzer (Cycle 2) — verify every indicator against hand-computed values, and make each safety property a failing-if-violated test
- **What happened:** Built the analytical core on top of the Cycle-1 read-only scaffold — Phases 3 (candle build/aggregate/provisional), 4 (indicator engine), 5 (regime + independent scoring + veto/guards + confidence + risk plan), 8 (look-ahead-safe backtest), 9 (paper trading + journal + no-order guard). Done inline (not via cold subagents) because the phases are tightly sequential .NET and each gated on a real `dotnet test` before the next. 55 net-new xUnit tests (82→137) + 19 Python still green. Every indicator (SMA/EMA/MACD/RSI-Wilder/ATR-Wilder/Bollinger/ADX/Stochastic/OBV) asserted against a *hand-computed* expected value with the arithmetic documented in the test, not "does not throw." The dangerous properties are each a dedicated test that fails if the property regresses: Buy/Sell independence (`Sell != 100 − Buy`), look-ahead safety (`LookAheadSafeWindow` throws on a future index; a peeking strategy faults inside the engine), and no-order-path (reflection over `IMt5BridgeClient` finds no trade verb; `PaperBroker` has no reference to it). The brief claimed "existing WPF placeholder screens"; there were none (Cycle 1 was headless), so Phase 6 UI was honestly deferred rather than faked.
- **Lesson:** "Verified against expected output" means a number you computed by another method, in the test, with the steps in a comment — pick tiny periods (RSI/ATR period 2, MACD 2/3/2) and clean datasets (linear series, pure trends where −DM≡0) so the expected value is hand-derivable and exact-ish (assert with a small tolerance for decimal EMA rounding). Independent buy/sell scoring is only real if the two draw from *separate evidence pools* — normalise each against the same max-weighted denominator but never subtract one from the other.
- **Rule going forward:** For any calc-heavy slice, each indicator/metric ships with a fixed-dataset test whose expected value is derived independently and documented inline; each safety invariant (no-fabrication / no-future-peek / no-order / independence) ships as a test that goes red the moment the property is violated. When a carried-over brief asserts an artifact exists ("existing WPF screens", "existing SQLite/EF setup"), verify it on the branch first — if it isn't there, build the testable pure-logic core and defer the shell honestly; never fake a dependency to look "done." Keep sequential, mutually-dependent implementation phases inline with a real build/test gate between each, rather than fanning out to cold subagents.

### 2026-07-31 — gold-signal-analyzer — headless xUnit green ≠ the exe actually runs; three real WPF defects only surfaced by a manual E2E pass
- **What happened:** After Cycle 5 (setup wizard) shipped with 200/0 xUnit passing and an explicit `dotnet build` of the WPF exe green, running the *actual built exe* end-to-end from a clean `%LOCALAPPDATA%` profile (driven via Windows UI Automation — `System.Windows.Automation`, since no browser/computer-use tool reaches a native desktop app) found the fresh-install flow was **completely broken**, in three ways none of the automated gates could catch: (1) `SetupWizardWindow.xaml` bound `TabControl.SelectedIndex` to a `private set` VM property with WPF's default `TwoWay` mode → `InvalidOperationException` on window open; (2) neither `App.xaml` nor `App.xaml.cs` set `ShutdownMode`, so the default `OnLastWindowClose` silently tore the `Application` down the instant the sole open gate dialog (disclaimer or wizard) closed — *before* `MainWindow.Show()` ran later in the same method — so the dashboard never appeared, with no exception at all; (3) a **latent Cycle 4 bug** — `<Run Text="{Binding Headline}"/>` in the notification template hit the same read-only-property/default-TwoWay trap (`Run.Text` also binds TwoWay by default), uncaught until this was the first time anyone's manual run actually reached the dashboard with an actionable signal. All three were root-caused from the crash's own stack trace/log (no guessing), fixed, and the fix re-verified by manually driving the full flow twice (disclaimer → wizard all 6 steps incl. the Mt5Live-blocked and non-loopback-rejected negative cases → dashboard renders → relaunch → both gates correctly skipped). `dotnet test` stayed 200/0 throughout — none of these were logic bugs the VM/store tests could have caught.
- **Lesson:** Headless xUnit tests over `ViewModelBase`-derived VMs (this codebase's whole "testable-VM/dumb-XAML" strategy) structurally cannot exercise **XAML binding-mode defaults** or **`Application.ShutdownMode`** — both are WPF-runtime behaviors with no VM-side surface to unit-test. `TabControl.SelectedIndex` and `Run.Text` (unlike `TextBlock.Text`) default to `TwoWay`/two-way-capable and will throw at runtime against any read-only VM property, silently invisible to a build or a headless test run. A sequence of gate dialogs shown via `ShowDialog()` before the main window exists is a shutdown-mode trap by default in every WPF app, not just this one.
- **Rule going forward:** For any WPF cycle that touches `.xaml` bindings or the `App.OnStartup` composition root, add a manual "run the built exe from a wiped `%LOCALAPPDATA%` profile" pass to the QA gate — this is a distinct check from `dotnet test`/`dotnet build`, not a subset of it. When binding a read-only (get-only or private-set) VM property in XAML, always state `Mode=OneWay` explicitly rather than relying on the target property's default (`TabControl.SelectedIndex`, `Run.Text`, and anything TwoWay-by-default will throw, not silently degrade). When showing one or more gate/dialog windows via `ShowDialog()` before the real main window is constructed, set `Application.ShutdownMode = OnExplicitShutdown` before the first `ShowDialog()` and switch to `OnMainWindowClose` right before the real main window's `.Show()` — never rely on the `OnLastWindowClose` default across a multi-dialog startup sequence. Windows UI Automation (`Add-Type -AssemblyName UIAutomationClient,UIAutomationTypes` in PowerShell) is a viable driver for native desktop-app E2E testing in this environment when no computer-use/screenshot tool is available (screen capture returned a black frame here — likely a non-interactive session — but the accessibility tree and `InvokePattern`/`SelectionItemPattern`/`ValuePattern` worked reliably for both inspection and control).
