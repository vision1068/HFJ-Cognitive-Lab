### 2026-06-22 — doh-flight-checker — .gitignore missed .env exclusion
- **What happened:** The project scaffold didn't exclude `.env`; caught later during the Market Compass security pass rather than at creation time.
- **Lesson:** Scaffolding steps silently skip security defaults unless checked explicitly.
- **Rule going forward:** Every new project's first commit must include a `.gitignore` that covers `.env`/`.env.local`/credentials — verified, not assumed (now in secure-coding.md checklist).

### 2026-07-02 — market-compass — GitHub Pages first deploy required manual settings
- **What happened:** Deploy failed 3× at `deployment_queued`: Pages source and Actions write-permissions had to be set manually in repo Settings before any workflow-based deploy could succeed; `enablement: true` was rejected ("Resource not accessible by integration").
- **Lesson:** First-ever Pages deployment on a repo is an account-settings problem, not a workflow problem — retrying the pipeline cannot fix it.
- **Rule going forward:** Before the first Pages deploy on any repo, confirm with the user: Settings → Pages → Source = GitHub Actions, and Settings → Actions → Workflow permissions = Read and write. Escalate to the user after 2 failed identical attempts (codex-rescuer rule 5).

### 2026-07-10 — market-compass — parallel sessions on one branch cause push rejections
- **What happened:** Multiple sessions pushed to `claude/jolly-newton-5uctey` simultaneously; pushes were rejected and required fetch+merge before every push, and one rerun failed on a stale duplicate artifact.

- **Rule going forward:** Always `git fetch` + merge before push; prefer a new triggering commit over rerunning a failed workflow when artifacts may be stale.

Prefer built-in drawing primitives over a charting library unless interactivity is a real requirement and the package is known-cached. Re-run the FULL solution build (not just new tests) after widening any shared constructor, and keep the always-visible disclaimer outside any scroll container. - **What happened:** Built the analytical core on top of the Cycle-1 read-only scaffold — Phases 3 (candle build/aggregate/provisional), 4 (indicator engine), 5 (regime + independent scoring + veto/guards + confidence + risk plan), 8 (look-ahead-safe backtest), 9 (paper trading + journal + no-order guard). - **Rule going forward:** For any calc-heavy slice, each indicator/metric ships with a fixed-dataset test whose expected value is derived independently and documented inline; each safety invariant (no-fabrication / no-future-peek / no-order / independence) ships as a test that goes red the moment the property is violated. ### 2026-07-31 — gold-signal-analyzer — headless xUnit green ≠ the exe actually runs; three real WPF defects only surfaced by a manual E2E pass
- **What happened:** After Cycle 5 (setup wizard) shipped with 200/0 xUnit passing and an explicit `dotnet build` of the WPF exe green, running the *actual built exe* end-to-end from a clean `%LOCALAPPDATA%` profile (driven via Windows UI Automation — `System.Windows.Automation`, since no browser/computer-use tool reaches a native desktop app) found the fresh-install flow was **completely broken**, in three ways none of the automated gates could catch: (1) `SetupWizardWindow.xaml` bound `TabControl.SelectedIndex` to a `private set` VM property with WPF's default `TwoWay` mode → `InvalidOperationException` on window open; (2) neither `App.xaml` nor `App.xaml.cs` set `ShutdownMode`, so the default `OnLastWindowClose` silently tore the `Application` down the instant the sole open gate dialog (disclaimer or wizard) closed — *before* `MainWindow.Show()` ran later in the same method — so the dashboard never appeared, with no exception at all; (3) a **latent Cycle 4 bug** — `<Run Text="{Binding Headline}"/>` in the notification template hit the same read-only-property/default-TwoWay trap (`Run.Text` also binds TwoWay by default), uncaught until this was the first time anyone's manual run actually reached the dashboard with an actionable signal. All three were root-caused from the crash's own stack trace/log (no guessing), fixed, and the fix re-verified by manually driving the full flow twice (disclaimer → wizard all 6 steps incl. the Mt5Live-blocked and non-loopback-rejected negative cases → dashboard renders → relaunch → both gates correctly skipped). `dotnet test` stayed 200/0 throughout — none of these were logic bugs the VM/store tests could have caught.
- **Lesson:** Headless xUnit tests over `ViewModelBase`-derived VMs (this codebase's whole "testable-VM/dumb-XAML" strategy) structurally cannot exercise **XAML binding-mode defaults** or **`Application.ShutdownMode`** — both are WPF-runtime behaviors with no VM-side surface to unit-test. `TabControl.SelectedIndex` and `Run.Text` (unlike `TextBlock.Text`) default to `TwoWay`/two-way-capable and will throw at runtime against any read-only VM property, silently invisible to a build or a headless test run. A sequence of gate dialogs shown via `ShowDialog()` before the main window exists is a shutdown-mode trap by default in every WPF app, not just this one.
- **Rule going forward:** For any WPF cycle that touches `.xaml` bindings or the `App.OnStartup` composition root, add a manual "run the built exe from a wiped `%LOCALAPPDATA%` profile" pass to the QA gate — this is a distinct check from `dotnet test`/`dotnet build`, not a subset of it. When binding a read-only (get-only or private-set) VM property in XAML, always state `Mode=OneWay` explicitly rather than relying on the target property's default (`TabControl.SelectedIndex`, `Run.Text`, and anything TwoWay-by-default will throw, not silently degrade). When showing one or more gate/dialog windows via `ShowDialog()` before the real main window is constructed, set `Application.ShutdownMode = OnExplicitShutdown` before the first `ShowDialog()` and switch to `OnMainWindowClose` right before the real main window's `.Show()` — never rely on the `OnLastWindowClose` default across a multi-dialog startup sequence. Windows UI Automation (`Add-Type -AssemblyName UIAutomationClient,UIAutomationTypes` in PowerShell) is a viable driver for native desktop-app E2E testing in this environment when no computer-use/screenshot tool is available (screen capture returned a black frame here — likely a non-interactive session — but the accessibility tree and `InvokePattern`/`SelectionItemPattern`/`ValuePattern` worked reliably for both inspection and control).
