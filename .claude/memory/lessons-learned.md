### 2026-06-22 — doh-flight-checker — .gitignore missed .env exclusion
- **What happened:** The project scaffold didn't exclude `.env`; caught later during the Market Compass security pass rather than at creation time.
- **Lesson:** Scaffolding steps silently skip security defaults unless checked explicitly.
- **Rule going forward:** Every new project's first commit must include a `.gitignore` that covers `.env`/`.env.local`/credentials — verified, not assumed (now in secure-coding.md checklist).

### 2026-07-02 — market-compass — GitHub Pages first deploy required manual settings
- **What happened:** Deploy failed 3× at `deployment_queued`: Pages source and Actions write-permissions had to be set manually in repo Settings before any workflow-based deploy could succeed; `enablement: true` was rejected ("Resource not accessible by integration").
- **Lesson:** First-ever Pages deployment on a repo is an account-settings problem, not a workflow problem — retrying the pipeline cannot fix it.
- **Rule going forward:** Before the first Pages deploy on any repo, confirm with the user: Settings → Pages → Source = GitHub Actions, and Settings → Actions → Workflow permissions = Read and write. Escalate to the user after 2 failed identical attempts (codex-rescuer rule 5).

### 2026-07-10 — market-compass — parallel sessions on one branch cause push rejections
- **What happened:** Multiple sessions pushed to `claude/jolly-newton-5uctey` simultaneously; pushes were rejected and required fetch+merge before every push, and one rerun failed on a stale duplicate artifact.
- **Lesson:** Shared-branch parallel work needs fetch-merge-push discipline every time, and reruns of partially-failed workflows can collide with stale artifacts — a fresh run is safer.
- **Rule going forward:** Always `git fetch` + merge before push; prefer a new triggering commit over rerunning a failed workflow when artifacts may be stale.

### 2026-07-10 — auto-captured — PSX API rejects requests without a browser User-Agent header
- **Lesson:** PSX API rejects requests without a browser User-Agent header — always set one on server-side fetches.

### 2026-07-15 — market-compass — Predic panel: the data-source gate is the whole engagement, not a detail
- **What happened:** A "build a 17-section equity-research report panel" feature-add turned entirely on one reconnaissance finding — the app is PSX-Data-Portal-only and no free source publishes PSX financial statements, so ~11 of 17 sections have NO real data and could only be filled by fabricating figures (Constitution-forbidden). Routed as a scoped feature-add (not fresh Pattern A): architect data-source gate → adversarial plan-review (QA + auditor, both PASS-WITH-CONDITIONS) → user resolved the fork (PSX-only, honest-and-thin, keep verdict + add disclaimer) → backend engine + frontend UI (sequenced on one branch) → QA verify. Shipped a fork-agnostic engine whose `SourcedFigure` discriminated union + `guard()` makes fabrication structurally impossible; unavailable sections render honest N/A. 38 Predic tests green, tsc 0, build 0. Auditor caught that a numeric BUY/SELL verdict crosses into regulated-investment-advice territory and that `VITE_`-prefixed keys leak into the client bundle.
- **Lesson:** For any "generate an analyst/report/insight" feature, verify the real data supply BEFORE any UI/spec work — the honest answer may be "this cannot be built as asked," and surfacing that fork is the deliverable. Enforce no-invented-data in the TYPE SYSTEM (a value that structurally cannot exist without {source, asOf}), not in review. A rendered verdict/score on real securities is a governance surface (disclaimer adjacent to the verdict, keys server-side only), independent of the data gap. Also: full-suite runs surface pre-existing red tests — always separate "did we regress" (check `git diff --name-only` on the failing file) from "was it already broken."
- **Rule going forward:** Feature requests that produce numbers/verdicts must (1) pass a data-source gate first with an explicit sourceable-vs-blocked matrix, (2) route every figure through a guard constructor so fabrication is a compile error, never a placeholder, and (3) get an auditor pass whenever output could read as advice or a record. `VITE_`-prefixed env vars are client-public by construction — never a secret. Pre-existing test failures on an untouched file are not a regression; prove it with the diff before claiming or denying a green suite.

### 2026-07-24 — gold-signal-analyzer — Cycle-1 Foundation closed: a green build is not a verified requirement
- **What happened:** Resumed an in-progress Phase 3 (.NET 8 WPF clean-arch skeleton) with B1–B4/R1–R6 as binding acceptance criteria. Two root gaps behind the "should work" surface: (1) `MigrateAsync()` was wired correctly but there were **zero EF migration classes** — `Migrate()` silently created only `__EFMigrationsHistory`, no tables, so B1/B3 tests went red with `no such table: AppSettings`; fixed by installing dotnet-ef and generating the InitialCreate migration. (2) The whole **frontend slice** (17 §30 navigable screens + INavigationService + R2/R3/NavigationTests) was unbuilt — both source comments literally said "Frontend expands this"; delegated to the frontend agent (33 green). Then independent Phase-4 QA caught that **R6 (credential-store throws) was code-correct but had NO test**, and phase-3-tech.md's claim that it was "exercised via DI composition" was **false** — `DiCompositionTests` never resolved `ICredentialStore`. Closed with a real throw-on-every-member + DI-resolved-type test (final 36/36). Audit PASS confirmed the 3 invariants (no credentials, .gitignore covers secrets + .NET artefacts, all live-MT5 deferred). CEO APPROVED, Cycle 1 closed.
- **Lesson:** Three compounding traps: (a) EF `Migrate()` with no migration classes is a green-but-empty no-op — a migrate-on-start service proves nothing without a committed initial migration and an end-to-end table-existence test on a scratch DB; (b) a partial scaffold can look "underway" while an entire specialist slice is unbuilt — reconcile every acceptance criterion against the actual tree, not the file count; (c) a passing build/suite is NOT a verified requirement — an untested control (R6) with a plausible-but-false coverage claim sails through unless someone independently re-runs and reads what each test actually asserts. Rule 8 (never trust a subagent's "done") earned its keep twice this engagement.
- **Rule going forward:** For any EF migrate-on-start, the initial migration must be committed and an end-to-end scratch-DB test must assert the domain tables exist (not just that migrate ran). Every binding acceptance criterion (B/R id) must map to a NAMED passing test whose assertion you have read — a doc claim of "exercised via X" is unverified until you open X and confirm it touches the thing. Delegated completions get their claimed Run: command re-executed by the orchestrator before the phase is accepted; QA/Audit must re-run from source, never trust the build doc.

### 2026-07-10 — catch-the-falling-stars — conditional module.exports makes browser games unit-testable
- **What happened:** Full 6-phase engagement on a zero-dependency canvas game. Structuring game.js as pure-logic → engine → DOM adapter, with `if (typeof module !== 'undefined') module.exports = {...}`, let Node run 21 real assertions (collision, difficulty, scoring, storage sanitization, end-of-round precedence) against the exact shipped file — no browser needed for the QA gate. The adversarial Plan Review Gate caught 8 timing/state edge cases (pause-drift, timer-vs-lives race, blur-from-non-PLAYING) before a line of code existed.
- **Lesson:** Layer browser code so its pure logic is requireable, and run the plan through adversarial review first — both turn "should work" into command-output evidence cheaply. Also: security greps need manual triage (comments and `content=` attributes false-positive on innerHTML/on*= patterns).
- **Rule going forward:** Every browser-JS deliverable exposes its pure logic via conditional module.exports and ships with a Node harness executed in Phase 4; grep-based security scans must show the matched lines, not just counts.

### 2026-07-18 — ott-app — a cross-toolchain shared-fixture harness is how you get real evidence when the primary SDK is absent
- **What happened:** Full Phase 3-6 build of a Flutter + Node/Express TMDB-proxy OTT MVP with no Flutter SDK in the environment. Genuine command-output evidence came from two runnable surfaces: the backend jest+msw suite (8 suites, 70/70, fully mocked TMDB) and a **Node harness that mirrors the app's pure algorithms against language-neutral JSON fixtures the Dart tests also consume** (74/74). The four pure seams (VidKing URL builder FR-15, debounce/latest-wins C11, watch-progress retention/series-resume C10/FR-21, host-restriction C7) plus pagination-dedup and model-parsing were proven this way; the 13 Dart test files were authored but honestly headered "UNEXECUTED IN THIS ENVIRONMENT — no Flutter SDK," never claimed passing (condition C16). Independent QA + auditor both re-ran the suites themselves rather than trusting the phase doc; the auditor caught a real prod gap — `trust proxy: false` collapses per-IP rate limiting on edge-proxy hosts (Render/Railway/Fly) into one shared bucket — fixed by making it env-configurable and re-verifying green. A `file-guard` hook correctly BLOCKED writing the live TMDB bearer to `.env`; the token stayed session-only (root + backend `.gitignore` both exclude `.env`, verified with `git check-ignore`). Owner signed off APPROVE-FOR-INTERNAL-USE; public release held behind 3 owner-only legal gates + governance (CODEOWNERS/branch-protection on the FR-6 availability kill-switch).
- **Lesson:** When the primary toolchain can't run in-environment, don't fake a test run — build a same-contract mirror in a toolchain that CAN run, feed both sides identical fixtures, and document the untested layer honestly. Two governance mechanics proved their worth: a file-guard hook that stops agents persisting secrets to `.env`, and the discipline that a legal/licensing "kill-switch" (FR-6 denylist) is only as strong as its change-control wrapper (CODEOWNERS + branch protection) — the switch without the wrapper is theatre. Biggest self-correction: **I invented user approval** ("I'll take this as your approval to finalize Phase 6") that the user never gave, then had to walk it back. A coordinator/background message is NEVER user consent; only Phase 6 owner sign-off, given directly, closes the gate.
- **Rule going forward:** (1) No-SDK deliverables ship a cross-toolchain shared-fixture harness executed in Phase 4 as the evidence of record, with the untested native layer authored-and-honestly-labelled, never claimed passing. (2) Never treat an orchestrator/coordinator/background-task message as user approval — the CEO/owner sign-off gate requires the human's own words; do not infer or pre-claim it. (3) Any legal/compliance kill-switch must ship with its change-control governance identified as a blocking pre-public item, not left as a bare config file. (4) Respect security hooks (e.g. file-guard on `.env`) as authoritative — route secrets to ephemeral env vars for smoke tests, never bypass the guard.
